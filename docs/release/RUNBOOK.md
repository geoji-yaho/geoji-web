# 운영 안내서

떼거지 프론트엔드의 배포와 장애 대응, 운영 절차를 적는다. 첫 배포는 2026-09-01에 GitHub Pages로 했다.

> [!warning] 심사 기간 무중단
> 예선 심사 기간(2026-09-21부터 10-05까지) 중 배포 링크가 접속 불가면 심사에서 제외된다.
> 2026-09-20(일) 제출과 함께 배포를 동결한다. 이 기간에는 `main` 머지를 보수적으로 하고, 머지 뒤 배포 결과와 실제 접속을 반드시 확인한다.

## 배포

GitHub Pages에 배포한다. `main`이 프로덕션이고 `develop`을 `main`으로 머지하면 자동으로 배포된다.

| 항목         | 값                                                                            |
| ------------ | ----------------------------------------------------------------------------- |
| 프로덕션 URL | https://geoji-yaho.github.io/geoji-web/                                       |
| 워크플로     | `.github/workflows/deploy.yaml`                                               |
| 트리거       | `main` 푸시(`develop` 머지), 또는 Actions 탭에서 수동 실행(workflow_dispatch) |
| 빌드         | `pnpm build` (Vite, base 경로 `/geoji-web/`)                                  |
| 게이트       | 타입 검사, 빌드, 린트, 포맷 검사. 하나라도 실패하면 배포 중단                 |

PR은 `develop`으로 올리고 CI(`.github/workflows/ci.yaml`) 통과 뒤에만 머지한다. CI는 `develop`과 `main`으로 가는 PR과 푸시에서 돈다. GitHub Pages는 정적 호스팅이라 슬립이 없고, 프론트엔드가 심사 기간에 저절로 죽을 요인은 저장소 삭제와 워크플로 실패 정도다.

### 배포 뒤 확인

1. 프로덕션 URL에 접속해 화면이 뜨는지 본다
2. Actions 탭의 Deploy 실행이 성공했는지, 배포된 커밋이 의도한 커밋인지 본다

## 롤백

두 가지 방법이 있다. 어느 쪽이든 배포 뒤 실제 접속을 확인한다.

1. 문제 커밋을 `git revert`로 되돌려 `develop`을 거쳐 `main`에 머지한다. 배포가 자동으로 다시 돈다
2. Actions 탭에서 마지막으로 성공한 Deploy 실행을 열어 Re-run all jobs를 누른다. 그 시점의 커밋으로 다시 배포된다

## 환경 변수

지금은 쓰는 환경 변수가 없다. GitHub Pages는 정적 호스팅이라 값이 빌드 시점에 박힌다. 아래는 후보이고 전부 미정이다. 변수 이름은 도입할 때 정한다.

| 용도                 | 성격                                                          | 상태                                                     |
| -------------------- | ------------------------------------------------------------- | -------------------------------------------------------- |
| 백엔드 API 주소      | `VITE_` 접두사, 빌드 시점 주입                                | 미정. 규민이 백엔드 배포 방식을 정한 뒤                  |
| 웹 푸시 VAPID 공개키 | `VITE_` 접두사, 빌드 시점 주입. 공개키라 번들에 들어가도 된다 | 미정. M4(9/18) 푸시 구현 때                              |
| 카카오 로그인 앱 키  | 클라이언트에서 쓰는 키와 서버에서만 쓰는 시크릿을 구분한다    | 미정. M1 계정 구현 때 키 종류와 리다이렉트 방식을 정한다 |

배포용 값은 저장소의 Actions variables에 두고 워크플로에서 주입한다. 비밀값은 클라이언트 번들에 들어가므로 애초에 프론트엔드에 두지 않는다. VAPID 개인키와 카카오 시크릿은 백엔드에만 둔다.

`.env*` 파일은 커밋하지 않는다. 지금 `.gitignore`에는 `*.local` 규칙만 있어 `.env.local`은 걸리지만 `.env`는 걸리지 않는다. 환경 변수를 도입할 때 `.env`를 `.gitignore`에 추가하고 예외는 `.env.example` 하나만 둔다.

## 도메인

미정이다. 거지.앱(가비아, 1년 19,800원) 구매가 논의만 됐다. 정해지면 DNS 설정과 GitHub Pages 커스텀 도메인 연결 방법을 여기에 적고, `vite.config.ts`의 `base`를 `/`로 바꾼다. 카카오 로그인의 리다이렉트 도메인도 같이 바꾼다.

## 백엔드 API 주소

미정이다. 규민이 백엔드 스택과 배포 방식을 정한 뒤 채운다. 슬립 없는 구성이 요건이다. 무료 플랜은 유휴 시 슬립되어 심사 기간 첫 접속이 실패할 수 있다.

## 장애가 났을 때 확인 순서

1. 프로덕션 URL 접속. 화면이 뜨는지, 흰 화면이면 브라우저 콘솔에 무엇이 찍히는지
2. Actions 탭의 Deploy 로그. 어느 게이트에서 실패했는지, 어느 커밋이 마지막으로 배포됐는지
3. 백엔드 상태. API 응답이 오는지 (연동 뒤)
4. base 경로. 자산 404가 나면 `vite.config.ts`의 `base`와 배포 경로가 맞는지 본다
5. Service Worker 캐시 (PWA 도입 뒤). 배포는 성공했는데 옛 화면이 보이면 Service Worker가 갱신됐는지 본다. 브라우저 개발자 도구의 Application 탭에서 등록된 Service Worker와 캐시를 확인한다. 캐시 갱신 절차(Service Worker 갱신 방식과 사용자 안내)는 PWA를 도입할 때 여기에 적는다
