# 운영 안내서

배포와 장애 대응, 운영 절차를 적는다. 첫 배포는 2026-09-01에 GitHub Pages로 했다.

> [!warning] 심사 기간 무중단
> 예선 심사 기간(2026-09-21부터 10-05까지) 중 배포 링크가 접속 불가면 심사에서 제외된다.
> 이 기간에는 `main` 머지를 보수적으로 하고, 머지 뒤 배포 결과와 실제 접속을 반드시 확인한다.

## 배포

GitHub Pages에 배포한다. `main`이 프로덕션이고 머지되면 자동으로 배포된다.

| 항목         | 값                                                            |
| ------------ | ------------------------------------------------------------- |
| 프로덕션 URL | https://geoji-yaho.github.io/geoji-web/                       |
| 워크플로     | `.github/workflows/deploy.yaml`                               |
| 트리거       | `main` 푸시, 또는 Actions 탭에서 수동 실행(workflow_dispatch) |
| 빌드         | `pnpm build` (Vite, base 경로 `/geoji-web/`)                  |
| 게이트       | 타입 검사, 빌드, 린트, 포맷 검사. 하나라도 실패하면 배포 중단 |

PR은 CI(`.github/workflows/ci.yaml`) 통과 뒤에만 머지한다. GitHub Pages는 정적 호스팅이라 슬립이 없고, 프론트엔드가 심사 기간에 저절로 죽을 요인은 저장소 삭제와 워크플로 실패 정도다.

## 롤백

두 가지 방법이 있다. 어느 쪽이든 배포 뒤 실제 접속을 확인한다.

1. 문제 커밋을 `git revert`로 되돌려 `main`에 머지한다. 배포가 자동으로 다시 돈다
2. Actions 탭에서 마지막으로 성공한 Deploy 실행을 열어 Re-run all jobs를 누른다. 그 시점의 커밋으로 다시 배포된다

## 환경 변수

지금은 쓰는 환경 변수가 없다. GitHub Pages는 정적 호스팅이라 값이 빌드 시점에 박힌다. 백엔드 주소가 생기면 `VITE_` 접두사 변수로 받고, 배포용 값은 저장소의 Actions variables에 두고 워크플로에서 주입한다. 비밀값은 클라이언트 번들에 들어가므로 애초에 프론트엔드에 두지 않는다.

`.env*` 파일은 커밋하지 않는다. `.gitignore`에 있고 예외는 `.env.example` 하나다.

## 도메인

미정이다. 거지.앱(가비아, 1년 19,800원) 구매가 논의만 됐다. 정해지면 DNS 설정과 GitHub Pages 커스텀 도메인 연결 방법을 여기에 적고, `vite.config.ts`의 `base`를 `/`로 바꾼다.

## 백엔드 API 주소

미정이다. 규민이 배포 방식을 정한 뒤 채운다. 슬립 없는 구성이 요건이다. 무료 플랜은 유휴 시 슬립되어 심사 기간 첫 접속이 실패할 수 있다.

## 장애가 났을 때 확인 순서

1. 프로덕션 URL 접속. 화면이 뜨는지, 흰 화면이면 브라우저 콘솔에 무엇이 찍히는지
2. Actions 탭의 Deploy 로그. 어느 게이트에서 실패했는지, 어느 커밋이 마지막으로 배포됐는지
3. 백엔드 상태. API 응답이 오는지 (연동 뒤)
4. base 경로. 자산 404가 나면 `vite.config.ts`의 `base`와 배포 경로가 맞는지 본다
