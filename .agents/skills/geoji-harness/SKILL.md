# geoji-harness

떼거지 웹에서 무언가를 만들 때의 진행 순서다. 명세를 확인하고 배치를 정하고 구현한 뒤 셋으로 나눠 검증한다.

혼자 다 하지 않는 이유는 셋이다. 검증하는 눈이 구현한 눈과 같으면 자기가 만든 것을 옳다고 읽는다. 명세 대조와 구현을 한 사람이 하면 문서에 없는 값을 자기도 모르게 채운다. 리뷰 세 관점은 서로 독립이라 같이 돌리면 시간이 들지 않는다.

## 쓰는 도구

이 저장소에서 쓸 수 있는 것은 `Agent`와 `SendMessage`다. `TeamCreate`와 `TaskCreate`는 없다. 팀을 만들려 하지 말고 이름을 붙인 서브 에이전트로 진행한다.

에이전트 정의는 `.claude/agents/`에 있다. `subagent_type`에 파일 이름을 확장자 없이 넣는다.

| subagent_type           | 하는 일                                  | 산출                                |
| ----------------------- | ---------------------------------------- | ----------------------------------- |
| `geoji-spec-auditor`    | 정본에서 무엇을 만들지 확인, 미결정 판정 | `_workspace/01_spec.md`             |
| `geoji-architect`       | 파일 배치와 공개 API, 타입 설계          | `_workspace/02_plan.md`             |
| `geoji-implementer`     | 구현                                     | 소스 파일과 `_workspace/03_impl.md` |
| `geoji-design-reviewer` | 시안과 토큰 대조                         | `_workspace/04_design_review.md`    |
| `geoji-code-reviewer`   | 구조와 타입, 접근성                      | `_workspace/04_code_review.md`      |
| `geoji-qa-verifier`     | 게이트와 브라우저 실물                   | `_workspace/04_qa.md`               |

호출은 이렇게 한다. `model`은 여섯 모두 `opus`다.

```
Agent({
  subagent_type: "geoji-spec-auditor",
  name: "spec",
  model: "opus",
  description: "명세 대조",
  prompt: "..."
})
```

`_workspace/`는 `.gitignore`에 있어 커밋되지 않는다. 중간 산출물을 남겨 두면 후속 요청에서 처음부터 다시 하지 않아도 된다.

일이 끝난 에이전트는 `SendMessage`로 `shutdown_request`를 보내 정리한다. 에이전트 정의의 `tools`에 `SendMessage`가 없으면 그 에이전트는 응답하지 못해 세션이 남는다. 도구를 좁힐 때 이것을 빼지 않는다.

## Phase 0. 어디서 시작할지 정한다

`_workspace/`를 보고 실행 모드를 고른다.

| 상태                           | 모드        | 시작 지점                                           |
| ------------------------------ | ----------- | --------------------------------------------------- |
| `_workspace/` 없음             | 초기        | Phase 1                                             |
| 있고 같은 대상을 고치라는 요청 | 부분 재실행 | 고칠 단계부터. 뒤 단계는 다시 돈다                  |
| 있고 다른 대상 요청            | 새 실행     | `_workspace/`를 `_workspace_prev/`로 옮기고 Phase 1 |

그리고 규모를 판정한다. 작은 일에 여섯을 부르면 기다리는 시간이 만드는 시간보다 길어진다.

| 규모 | 무엇                                      | 부르는 에이전트                                          |
| ---- | ----------------------------------------- | -------------------------------------------------------- |
| 작음 | 공통 컴포넌트 하나 추가나 수정, 토큰 하나 | implementer, code-reviewer. 명세 대조와 설계는 직접 한다 |
| 보통 | 화면 하나                                 | 여섯 전부. 구현은 1명                                    |
| 큼   | 화면 여럿, feature 신설                   | 여섯 전부. 구현은 파일을 나눠 최대 3명                   |

규모를 정했으면 사용자에게 한 줄로 알린다. 무엇을 만들고 누구를 부르는지.

## Phase 1. 명세를 대조한다

`geoji-spec-auditor` 1명. 요청 원문과 짐작되는 화면 ID를 넘긴다.

```
prompt: |
  요청: {사용자 원문}
  짐작되는 화면: {S-XX 또는 "모르겠음"}

  docs/design/DESIGN-SPEC.md와 docs/product/SPEC.md에서 대상을 확정하고
  _workspace/01_spec.md에 정의된 형식으로 쓴다.
  미결정에 걸리는 것이 있으면 blocked 절에 남기고 임시 기본값을 제안하지 않는다.
```

## 게이트 A. 미결정이면 멈추고 묻는다

`_workspace/01_spec.md`의 `blocked`가 비어 있지 않으면 **여기서 멈춘다.** `AskUserQuestion`으로 묻고 답을 받은 뒤에 진행한다.

이 저장소는 미결정 값을 코드에 박기 전에 묻기로 되어 있다. 협의 중인 값에 그럴듯한 기본값을 채우면 그것이 사실상 확정이 된다. 나중에 결정이 다르게 나면 이미 쓴 코드를 되돌려야 한다.

화면을 만들 때 가장 자주 걸리는 것은 라우터다. 지금 라우터는 미도입이고 화면 14개를 어느 feature로 묶을지도 정하지 않았다. 첫 화면 요청이면 거의 반드시 걸린다.

질문에는 선택지를 함께 낸다. 무엇이 왜 막혔고 각 선택이 무엇을 바꾸는지 적는다.

## Phase 2. 배치를 설계한다

`geoji-architect` 1명. `_workspace/01_spec.md`를 읽으라고 알린다.

```
prompt: |
  _workspace/01_spec.md를 읽고 배치를 설계해 _workspace/02_plan.md에 쓴다.
  게이트 A에서 정해진 것: {사용자 답변, 없으면 "없음"}
```

## 게이트 B. 승인이 필요하면 묻는다

`_workspace/02_plan.md`의 `approval`이 비어 있지 않으면 멈추고 묻는다. feature 신설과 의존성 추가, `src/shared/` 시그니처 변경, 토큰 변경이 여기 해당한다.

`approval`이 비어 있으면 사용자를 부르지 않고 Phase 3으로 간다.

## Phase 3. 구현한다

`geoji-implementer`. 규모가 큼이면 설계의 파일 목록을 겹치지 않게 나눠 최대 3명까지 한 메시지에서 동시에 부른다. 같은 파일을 둘에게 주지 않는다. 나중에 쓴 쪽이 앞선 것을 지운다.

```
prompt: |
  _workspace/02_plan.md와 _workspace/01_spec.md를 읽고 구현한다.
  네 몫: {파일 목록}
  다른 담당이 맡은 파일: {목록}. 건드리지 않는다.
  _workspace/03_impl.md에 보고를 쓴다. 여럿이면 03_impl_{n}.md에 쓴다.
```

## Phase 4. 셋으로 나눠 검증한다

`geoji-design-reviewer`와 `geoji-code-reviewer`, `geoji-qa-verifier`를 **한 메시지에서 동시에** 부른다. 서로 읽는 것도 보는 것도 달라 순서가 필요 없다.

```
prompt: |
  방금 구현한 것을 검토한다. _workspace/의 03_impl*.md 전부에 목록이 있다.
  이번에 쓴 보고서: {실제 파일 목록}
  자기 담당 파일에 정해진 형식으로 쓴다.
```

## Phase 5. 고치고 보고한다

세 보고서를 읽고 오케스트레이터가 직접 고친다. 고치는 에이전트를 또 부르지 않는다. 지적은 대개 몇 줄이고, 부르는 비용이 고치는 비용보다 크다.

1. 같은 줄이나 같은 원인을 가리키는 지적을 하나로 합친다
2. 심각도 높음부터 고친다
3. 고치지 않는 것은 이유를 적는다. 의도된 동작을 바꾸게 되거나 이번 범위 밖이거나 근거 없는 취향이면 넘긴다
4. `pnpm check`를 다시 돌린다. 통과할 때까지 고친다
5. 같은 게이트가 세 번 반복 실패하면 더 시도하지 않는다. 변경을 되돌리고 설계를 다시 본다

보고는 이렇게 한다.

```markdown
## 만든 것

| 경로 | 무엇 |

## 검증

| 관점 | 판정 | 남은 것 |
| 디자인 | | |
| 코드 | | |
| 동작 | | |

## 고친 것

검토 지적 중 반영한 것.

## 넘긴 것

반영하지 않은 것과 이유.

## 확인하지 못한 것

브라우저로 못 본 상태, 미결정이라 비워 둔 값.
```

커밋하지 않는다. 사용자가 커밋해라고 하거나 `/git:commit`을 부를 때만 커밋한다.

마지막에 한 줄로 묻는다. 고칠 곳이 있는지, 워크플로우에서 바꾸고 싶은 것이 있는지.

## 에러

| 무슨 일                          | 어떻게                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| 에이전트가 빈 결과나 실패를 반환 | 같은 프롬프트로 한 번만 다시 부른다. 또 실패하면 그 단계 없이 진행하고 보고서에 누락을 적는다 |
| 산출 파일이 없음                 | 다음 단계를 시작하지 않는다. 앞 단계를 다시 부른다                                            |
| 검토 지적이 서로 어긋남          | 지우지 않는다. 양쪽을 보고서에 함께 적고 어느 쪽을 따랐는지 밝힌다                            |
| 게이트 3회 반복 실패             | 되돌리고 설계로 돌아간다. 네 번째를 시도하지 않는다                                           |
| 브라우저 도구 응답 없음          | 두세 번에서 멈춘다. 게이트 결과만으로 보고하고 실물을 못 봤다고 적는다                        |

## 자세한 것

| 파일                             | 언제 읽는가                           |
| -------------------------------- | ------------------------------------- |
| `references/screen-build.md`     | 화면을 조립하는 순서와 자주 틀리는 것 |
| `references/review-checklist.md` | 검토 항목 전체                        |
| `references/quality-gate.md`     | 게이트 실행과 브라우저 확인 절차      |

에이전트들이 각자 필요한 것을 읽는다. 오케스트레이터가 미리 읽어 프롬프트에 넣지 않는다. 컨텍스트만 늘고 에이전트는 어차피 자기 파일을 다시 읽는다.

## 테스트 시나리오

**정상.** "지출 등록 화면 만들어줘"가 들어온다. Phase 0이 보통 규모로 판정한다. spec-auditor가 S-09를 찾고 무엇을 필드가 필수 30자라는 것과 `AmountField`, `AttachmentField`, `Chip`을 쓸 수 있다는 것을 적는다. `blocked`에 라우터와 API 규약이 잡혀 게이트 A에서 멈춘다. 사용자가 "라우터 없이 카탈로그에 붙여라"라고 답하면 architect가 `features/post/`를 제안하고 feature 신설이라 게이트 B에서 다시 묻는다. 승인 뒤 구현하고 셋이 검증한다. design-reviewer가 `text-[15px]`를 잡고 qa-verifier가 360에서 가로 스크롤을 잡는다. 둘 다 고치고 게이트를 통과시킨 뒤 보고한다.

**에러.** 같은 요청에서 qa-verifier의 브라우저 도구가 세 번 응답하지 않는다. 게이트 결과만 적고 실물을 못 봤다고 보고에 남긴다. 판정을 통과로 적지 않는다.
