# 화면 리뷰

## 소유하는 룰

`docs/design/DESIGN-SPEC.md`의 공통 규칙과 반응형, 화면별 명세 절. 카피 톤은 `docs/design/DESIGN.md` 카피 톤 절이다. 위키와 코드가 어긋나는 것이 `docs/product/SPEC.md` 확인 필요 절에 이미 적혀 있으면 어긋남이 아니다. Tailwind 값은 review-tailwind, 데이터가 오는 길은 review-data 몫이다.

## 검수에서 판단하는 것

- 명세의 상태를 다 그리는가. 빈 결과와 실패가 같은 화면이면 서버를 못 읽은 것이 "방이 없어요"로 보인다
- 로딩 자리가 정상 화면과 같은 높이를 잡는가. 다르면 데이터가 오는 순간 배치가 튄다
- 명세에 있는 요소가 빠졌거나 명세에 없는 것이 생겼는가. 둘 다 적고 어느 쪽이 맞는지 단정하지 않는다
- 키보드로 되는가. `onClick`이 달린 `div`, `outline-none`, 보이는 순서와 다른 포커스 순서, 시트와 모달을 연 뒤 포커스가 안에 머무는가
- 읽어 줄 이름이 있는가. 아이콘 버튼의 `aria-label`, 입력의 라벨, 도장과 뱃지처럼 색으로만 뜻을 전하는 것, 상태 변화의 `role="status"`
- 눌리는 것이 눌리는 것처럼 보이는가. `pressable`과 `disabled` 상태, 처리 중에 버튼이 잠기는가
- 360과 393에서 깨지는가. 화면보다 넓은 고정 폭, 줄바꿈 막힌 긴 닉네임, 가로 스크롤
- 카피가 존댓말이면서 신랄한 톤인가. 판결 5종 이름과 서비스명 떼거지가 맞는가

파일 이름과 한 파일 한 컴포넌트, `PropsWithChildren`, JSX `{" "}`는 스크립트가 잡는다.

## 자문에서 답하는 것

화면 하나의 명세 절을 받아 상태마다 무엇으로 그릴지(`shared/ui`의 어느 컴포넌트, 빈 상태 문구)와 포커스 순서를 답한다.
